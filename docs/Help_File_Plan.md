# A reference `help.txt` for MMBasic — plan

Status: P0-P2 and P4 built, 2026-09-17; supplementary manuals folded in
2026-09-18. Three files - `docs/help.txt` (569 KB, 1151 topics),
`docs/helpmin.txt` (250 KB) and `docs/helptiny.txt` (108 KB) - are generated by
`tools/gen_help.py` and pass `tools/help_lint.py` with no errors. Not yet tested
on a board (P4's second half), and no per-variant filtering yet (see §8).

Goal: ship an official, comprehensive `A:/help.txt` generated from the user
manual and validated against the firmware, replacing the ad-hoc user-made files
that circulate today.

---

## 1. What `HELP` actually does

`cmd_help()` — [Commands.c:3054](../core/Commands.c#L3054) — plus one special
case in the tokeniser, [MMBasic.c:1242](../core/MMBasic.c#L1242). The file
format is entirely defined by those ~80 lines of code, so the rules below are
the contract the generator has to satisfy. Several of them are sharp edges that
the existing user files fall foul of.

| Behaviour | Consequence for the file |
|---|---|
| `tokenise()` auto-quotes everything after `HELP ` at the start of a line | `HELP PRINT`, `HELP MATH FFT` and `HELP MM.INFO(OPTION)` all work unquoted; the argument is the **whole rest of the line**, spaces included |
| Topic headers are lines starting with `~`; the body is every line until the next `~` | One `~` per topic. A body line must never begin with `~` |
| Match is `pattern_matching(user, header, 0, 0)` — FatFs, [ff.c:3182](../third_party_mod/ff.c#L3182) | **Whole-string** match, case-insensitive, `?`/`*` wildcards supplied by the *user*, not the file. `HELP PRINT` matches a header of exactly `PRINT` — and nothing else |
| Header compared verbatim | **No trailing space** on a `~` line, ever. `~MM.DEVICE$ ` is unreachable except via `MM.DEVICE$*` |
| Body lines printed through `printWrappedText(buff, Option.Width - 1, ...)` | Long lines re-wrap to the console width at word boundaries. Tabs are not expanded |
| Line read into `GetTempStrMemory()` — 256 bytes — with **no bounds check** ([Commands.c:3072](../core/Commands.c#L3072)) | Any line of 256 characters or more corrupts the temp-string pool. Hard cap the generator at ~200 |
| After a body, the next `~` is un-read with `lfs_file_seek(..., -(strlen(buff) + 2), ...)` | The arithmetic assumes **CRLF**. Emit CRLF |
| `ListNewLine()` pauses with `PRESS ANY KEY ...` every `Option.Height - overlap` lines | Keep a topic to roughly one or two screens; long entries are legal but tedious |
| Path is hard-coded `A:/help.txt`, lower case, LittleFS is case-sensitive | The file must be on the internal flash drive, named exactly `help.txt` |
| No match ⇒ nothing is printed at all | The file should carry an index topic so a miss is recoverable |
| `HELP` is `#ifndef PICOMITEMIN` ([AllCommands.h:658](../AllCommands.h#L658)) | PICOMIN has no HELP; 16 of the 17 variants do |

### What this means for the attached user file

It was clearly machine-extracted from the manual's syntax lines, which makes
almost every topic unreachable by name: `~MM.DEVICE$ ` and
`~PRINT expression [[,; ]expression] ... etc` only match if the user guesses the
exact string or types a wildcard. Each header is also duplicated as the first
body line — a workaround for the same problem. It is a good demonstration of why
the header has to be the *name*, not the *syntax*.

## 2. Design of the reference file

**One topic per header, header = the canonical name, upper case, no trailing
space.** The syntax goes in the body, where it belongs.

```
~PRINT
PRINT expression [[,; ]expression] ... etc
PRINT #nbr, expression [[,; ]expression] ... etc
PRINT @(x [, y]) expression

Outputs text to the console followed by CR/LF.  Multiple expressions
must be separated by a comma (tab), a semicolon (nothing), or a space.
A trailing ; or , suppresses the CR/LF.
  ? is a shortcut for PRINT.
See also: PRINT @, FORMAT$, STR$, TAB, OPEN, LONGSTRING PRINT
```

Rules the generator enforces:

- **Hierarchical names.** `~MATH`, `~MATH FFT`, `~MATH SENSORFUSION`,
  `~SPRITE LOAD`, `~OPTION LCDPANEL`. `HELP MATH` gets the family overview,
  `HELP MATH*` gets every member. This is what makes the whole-string matcher
  pleasant rather than hostile.
- **ASCII only.** The manual is full of smart quotes, en-dashes and `…`;
  the console is 7-bit (`tokenise()` masks with `& 0x7f`). Transliterate.
- **Hard-wrap at 78 columns**, cap every line at 200 characters. 78 reads
  correctly on an 80-column console and degrades to clean double-wrapping on a
  40-column LCD.
- **Tabs expanded**, embedded manual tables re-laid-out as aligned two-column
  text or dropped to the long-form manual.
- **Variant note as the first body line** where one applies, using a controlled
  vocabulary (`[VGA/HDMI only]`, `[RP2350 only]`, `[WiFi versions only]`).
- **`See also:` last line**, harvested from cross-references so related topics
  are discoverable.
- **Index topics**: `~HELP` (how to use it, wildcards), `~COMMANDS`,
  `~FUNCTIONS`, `~OPTIONS`, `~VARIABLES` listing names by family, plus family
  overviews (`~MATH`, `~SPRITE`, `~WEB`, …).
- Aliases cannot be chained (a matched header's body stops at the next `~`), so
  an alias like `?` gets its own short topic pointing at the real one.

## 3. Sources

### 3.1 The manual is the spine

`docs/PicoMite_User_Manual.docx` already holds the detailed listings as
**tables**, name in column 0, description in the last column — the same
structure `docs/add_manual_bookmarks.py` reads:

| docx table | Section | Rows |
|---|---|---|
| 14 | Predefined read-only variables | 40 |
| 15 | Options | 86 |
| 16 | Commands | 383 |
| 17 | Functions | 105 |
| 18 | Obsolete commands and functions | 15 |
| | **total** | **629** |

That is a directly harvestable 629-topic corpus, ~325 KB of description text,
and it is text you already maintain — so the help file stays in step with the
manual for free.

`clean_name()` in `add_manual_bookmarks.py` already solves the "turn a syntax
cell into a canonical name" problem (all-caps prefix, stop at `(` or `,`,
symbol commands kept verbatim). Reuse it rather than writing a second one.

### 3.2 The code is the authority on existence and variants

The manual annotates only **55 of the 629** entries with a version restriction,
in free text ("WIFI VERSIONS ONLY", "RP2350 VERSIONS ONLY.", "VGA AND ALL RP2350
VERSIONS ONLY"). That is neither complete nor machine-readable, so availability
comes from the firmware instead:

- **Top-level keywords**: preprocess `AllCommands.h` once per `COMPILE` variant
  (the 17 in [CMakeLists.txt:6](../CMakeLists.txt#L6)) and diff the resulting
  `commandtbl` / `tokentbl` name lists. This is the same preprocessor-exact
  method used for the 6.03.02 manual audit; that phase-00 tooling was
  scratchpad-only and needs rebuilding as a proper script.
- **Second-level keywords** (`MATH FFT`, `SPRITE LOAD`, `OPTION ...`) are not in
  the token table — they are `checkstring()` literals inside the handler. Sweep
  the `cmd_*` sources for `checkstring(p, "LITERAL")` and attribute each literal
  to its owning command; this both finds sub-commands the manual missed and
  gives them variant gating from the enclosing `#ifdef`.
- `OptionMap[]` is the maintained table for OPTION names — use it for the OPTION
  topics rather than re-deriving them from the manual.

## 4. Size budget

Measured from the manual text, plus CRLF and layout overhead:

| File | Content | Size |
|---|---|---|
| `help.txt` (full) | every topic, full description | **569 KB** (as built) |
| `helpmin.txt` (short) | syntax + first two sentences + see-also | **250 KB** (as built) |
| `helptiny.txt` (syntax) | syntax lines only | **108 KB** (as built) |

Against the A: drive, computed from `configuration.h`
(flash size − `RoundUpK4(TOP_OF_SYSTEM_FLASH)`), **to be confirmed against
`MM.INFO(DISK SIZE)` on real boards**:

| Variant | A: capacity (calc) | Full fits? |
|---|---|---|
| PICO (RP2040, 2 MB) | ≈ 636 KB | yes, but takes 59% of the drive |
| VGA (RP2040, 2 MB) | ≈ 828 KB | yes |
| WEB (RP2040, 2 MB) | ≈ 380 KB | **no** |
| PICORP2350 (2350, 4 MB) | ≈ 1.8 MB | comfortably |

So two generated files, not one, and the short one is the default recommendation
for RP2040 boards. Per-variant filtering is *not* a useful size lever — the
variant-only material is only ~53 KB — so filtering is about correctness (not
offering HDMI commands on a VGA build), not about fitting.

## 5. Work plan

**P0 — contract and harness.** Write `tools/help_lint.py`: a faithful Python
replica of the `cmd_help()` reader (same line splitting, same rewind arithmetic,
same `pattern_matching`). It answers "does `HELP X` find topic X?" for every
topic, and flags trailing spaces, over-long lines, non-ASCII bytes, LF-only
endings, `~` in a body, and orphan `See also:` targets. Everything downstream is
checked with it. Deliverable: the linter, run against the attached user file to
prove it catches that file's faults.

**P1 — harvest.** `tools/gen_help.py --harvest` → `docs/help_topics.json`:
one record per manual row (name, syntax lines, description, section, source row).
Reuse `clean_name()`. Deliverable: 629 records plus a report of rows whose name
could not be derived.

**P2 — reconcile against the code.** `tools/help_variants.py`: per-variant token
tables from the preprocessor, plus the `checkstring` sweep. Produces three
lists — in the firmware but not in the manual (documentation gaps, valuable in
their own right), in the manual but in no variant (obsolete), and a per-topic
variant mask. Deliverable: the diff report, which should feed manual corrections
as well as the help file.

**P3 — author the deltas.** Hand-write what the harvest cannot produce: the
index topics, family overviews, the `See also:` graph, alias stubs, and the
topics P2 showed as missing. This is the only genuinely manual step and is the
bulk of the calendar time.

**P4 — emit and verify.** `gen_help.py --full` / `--short` / `--variant=VGA`.
Lint, then real-board tests on the PC3 rig: `HELP`, `HELP PRINT`, `HELP MATH*`,
`HELP *SPRITE*`, a deliberate miss, a topic with an embedded table, a 40-column
LCD console, and `HELP` on a nearly-full A: drive.

**P5 — ship and keep it honest.** `help.txt` + `helpmin.txt` as release assets;
`docs/HELP_File_Format.md` so users writing their own get the rules right; a
`release_preflight.py` check that the shipped help file lints clean and that its
topic list still matches the current manual and token tables.

## 6. Firmware changes worth discussing (none assumed)

Not part of the file work, and not to be done without agreement — but the file
work exposed them:

1. **Bound the line read.** `while (1) { ...; *in++ = c; }` has no length guard
   against a 256-byte buffer, so a malformed third-party help file corrupts
   memory today. One-line fix.
2. **Say when nothing matched.** A miss currently prints nothing at all.
3. **Retry with an implicit `*`** when an exact match yields no hits, so
   `HELP MATH` lists the family instead of failing silently.
4. **Look beyond `A:`** — fall back to the current drive, so SD-card users can
   carry the full file without spending internal flash.
5. **`HELP` with no argument** could print the `~HELP` index topic rather than
   the present two-line hint.

Items 2–5 change behaviour users may depend on; 1 is a straight bug fix.

## 7. What was actually built

| File | What it is |
|---|---|
| `tools/gen_help.py` | harvests the manual, emits `help.txt` / `helpmin.txt` |
| `tools/help_lint.py` | the firmware's reader in Python; checks and previews |
| `tools/help_gaps.py` | diffs the supplementary manuals against the help file |
| `docs/help.txt` | 1151 topics, 569 KB |
| `docs/helpmin.txt` | the same 1151 topics, syntax plus a summary, 250 KB |
| `docs/helptiny.txt` | the same 1151 topics, syntax only, 108 KB |
| `docs/HELP_File_Format.md` | the format, for users writing their own |

Harvest results: 628 manual rows, 596 of which split cleanly into one topic per
syntax form by pairing the blank-line-separated groups in the name and
description cells. The other 32 are rows where several syntax forms share one
description (`MEMORY SET`, `GUI CURSOR`, `MANDELBROT`); those become a single
topic under the shared prefix, with every other form reachable as a
cross-reference stub. 671 topics carry text, 196 are stubs and family pointers.

Beyond the plain harvest the generator adds:

- `~OPERATORS` and `~ESCAPE CODES`, built from the manual's operator and escape
  tables, which have no detailed-listing row of their own.
- `MM.INFO(X)` / `MM.INFO$(X)` pairing — the manual documents each enquiry under
  one spelling only, so the other spelling gets a stub.
- Alias and family stubs driven by `AllCommands.h`: every name in the firmware
  token table is either a topic, a stub (`COLOR` -> `COLOUR`, `END IF` ->
  `ENDIF`, `EXIT FOR` -> `EXIT DO`) or a family pointer (`HELP CPU` lists
  `CPU RESTART`, `CPU SLEEP`, `CPU SPEED`).

**Collective tokens are excluded.** Several user-facing functions share one
token so the function table stays under the 128 a 7-bit token allows -
`BIN$`/`OCT$`/`HEX$` are all `BASE$`, `LCASE$`/`UCASE$`/`LEFT$`/`RIGHT$` are all
`SCHANGE$`, `MIN`/`MAX` are `TOPBOTTOM`, and `PEEK(BYTE` is `PEEK(INT8`. The
generator reads those rewrites out of `tokenise()` ([MMBasic.c:1270](../core/MMBasic.c#L1270))
rather than keeping a list, so a collective added later is hidden automatically.
It prints what it hid on every run. The user-facing spellings all keep their own
topics; only the internal names are suppressed.

`BASE$` is the exception and is documented, because it is the only way to reach
a base other than 2, 8 or 16 - `BASE$(12, 100)` prints `84`. No manual covers
it, so its topic is hand-written in `HANDWRITTEN` in the generator, and being
in that table is what un-hides it.

A second harvester covers the supplementary manuals, where the User Manual
carries only a pointer row - see `docs/Help_Coverage_Review.md`. It contributes
291 of the topics.

That cross-check now leaves **two firmware keywords with no entry anywhere**:
`BASE$` and `SCHANGE$`. Worth fixing in the manual rather than papering over in
the help file.

## 8. Still to do

- **On-board testing.** Nothing has been run on real hardware yet: `HELP` on a
  40-column LCD console, a topic with an embedded table, paging behaviour, and
  the install on a nearly-full A: drive.
- **Per-variant filtering** (P2's second half). The generator cross-checks
  against the union of all variants in `AllCommands.h`; it does not yet
  preprocess per `COMPILE` value, so a VGA build's help file still offers HDMI
  topics. Needs the preprocessor-exact token tables and the `checkstring` sweep
  described in §3.2.
- **`See also:` quality.** Currently derived from "See the XXX command" phrases
  in the manual text - accurate where it fires, but sparse.
- **Release wiring** (P5): ship both files as release assets and add a
  `release_preflight.py` check that they lint clean and still match the manual.

## 9. Open questions

- Real `MM.INFO(DISK SIZE)` free space on a stock PICO and on a WEB RP2040
  build — the table in §4 is calculated, not measured.
- Two files (`help.txt` / `helpmin.txt`) or one full file plus a documented
  `gen_help.py` users can re-run? My preference is two, shipped.
- Should the OPTION topics be in the same file or a separate `options.txt`?
  They are 39 KB of the total and are rarely wanted mid-program.
- Wrap at 78 columns as proposed, or leave whole paragraphs on one line (≤ 200
  chars) and let `printWrappedText` do all the wrapping? The latter adapts
  better to 40-column panels but splits long paragraphs at arbitrary points.
